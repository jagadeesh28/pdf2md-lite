## 1. Executive Summary

The project is in excellent architectural shape: a clean monorepo split (`engine` / `cli` / `server` / `desktop` / `ui`), strict offline-only discipline, a strong ADR culture, deterministic zero-weight fallbacks (geometric tables, XY-Cut++, regex metadata), and a real content-hash `--resume` path (verified in `crates/engine/src/batch.rs:331–344`, which compares the frontmatter `pdf_sha256` against `compute_file_sha256`). Quality gates are comprehensive (96/96 tests at last review; clippy `-D warnings`).

Three structural themes dominate every recommendation below:

1. **Dual inference runtimes & unaccelerated execution** — `tract-onnx` runs Indra OCR + YOLO; `ort` runs SLANet / RapidLaTeXOCR / GLiNER / embeddings. All ORT sessions use `GraphOptimizationLevel::Level1` with **no execution provider** (CPU only). This is the direct cause of the baseline profile's ~95.5% user CPU in tensor math and ~21 s/doc.
2. **The model stack is "good but dated"** — every model has a measurably stronger open-source successor that still satisfies the offline constraint.
3. **The UI is polished but the flagship "Split-Pane Inspector" is half-wired** — the **left "SOURCE PDF CANVAS" pane is never populated** (`previewUrl` is read in `ui/src/components/SplitPane.tsx:160` but set nowhere), and the CLI's `--help` is hand-rolled while `clap` (derive) sits unused in the workspace dependency graph.

## 2. Performance Recommendations

### P0 — Unlock hardware acceleration & consolidate the runtime (biggest single win)

- **Evidence**: `crates/engine/src/figure/models.rs:42` builds a shared ORT `Environment` with no execution provider; every session (`figure/latex.rs:71`, `figure/slanet.rs:69`, `metadata/gliner.rs:77`, `embeddings/engine.rs:57`) uses `GraphOptimizationLevel::Level1`.
- **Recommendations**:
  1. **Add execution-provider (EP) selection** — on Windows try `DirectML` (GPU/NPU), then `OpenVINO` / `oneDNN` for CPU, then fall back to the default CPU EP. This alone can yield a 10–50× speedup on the tensor-heavy paths on machines with a GPU.
  2. **Raise optimization to `GraphOptimizationLevel::Level3`** and set intra-/inter-op thread counts explicitly (today they are defaults and can oversubscribe against the concurrency governor in `concurrency.rs`).
  3. **Consider consolidating all models on ORT** (ORT can also run Indra and YOLO). This removes the double-runtime resident footprint and lets the conservative 350 MB base-session cost in `concurrency.rs:36` shrink → more page workers on the same RAM. *Tradeoff*: `tract-onnx` is the pure-Rust philosophical anchor (ADR 0001 / 0005). If it must be retained, at minimum isolate ORT models onto an accelerated EP.

### P1 — Eliminate remaining serialization & widen batching

- **Batch the world/Indic recognizer** — `backends/indra/engine.rs` (`transcribe_image_with_script`) routes **only English/Latin** through `recognize_lines_batch`; Telugu / World / Auto stay per-line. Non-Latin documents therefore forfeit the single largest CPU optimization in the project. Extend the batched plans to `rec_world.onnx`.
- **Session pools instead of a single `Mutex<Session>`** — RapidLaTeXOCR and SLANet each hold one `Mutex<Session>`. Formula-heavy pages still serialize behind one session across all page workers. Add a small per-model pool (2–4 sessions) to realize the "Concurrent Neural Session Dispatch" idea already present in `GLOSSARY.md` but not yet implemented.
- **Pipelined rasterization ↔ inference** — ADR 0007 names pipelined rasterization; `stream_rendered_pages` already streams pages from `hayro`, but layout / OCR / tables / LaTeX remain sequential per page. Overlapping rendering of page N+1 with inference on page N would hide rendering latency.
- **Tensor buffer pooling** — `backends/indra/detect.rs` and `backends/indra/recognize.rs` allocate fresh `Vec<f32>` tensors every line/page. Reuse arena-pooled buffers to cut allocation churn (contributing to the ~4.5% kernel/paging time in profiling).

### P2 — Smaller wins

- **Release profile**: `lto = "thin"` → `"fat"` (slower builds, better generated code) — see workspace `Cargo.toml:54`.
- **Page-level detection cache**: keyed by SHA-256 of the page raster so `--watch` / re-runs skip re-detecting unchanged pages.
- **DPI / scale tuning**: `hayro` renders at 2×; make DPI configurable so text-only documents can rasterize lower, saving both RAM and inference cost.
- `concurrency.rs` base / per-worker constants (350 MB / 200 MB) are hardcoded; expose them via `AppConfig` for tuning on high-RAM hosts.

## 3. Model Recommendations ("better conversion")

Every recommended model is offline, MIT/Apache-licensed, and has an ONNX export, so the zero-cloud constraint in ADR 0001 is preserved. The "pure-Rust" preference is unaffected because these models run through the existing ORT path.

| Pipeline stage | Current | Recommended upgrade | Expected impact |
|---|---|---|---|
| **Formula OCR** | RapidLaTeXOCR (encoder + decoder pair) | **UniMERNet** (MIT) or **TexTeller** (UniMERNet-based) | Largest quality win; far better inline-vs-display math and cleaner output → far less reliance on the brittle hand-rolled repair heuristics in `figure/latex.rs` (`balance_braces`, `fix_common_latex_command_typos`) and the ~2,894-line self-repair logic in `markdown.rs`. |
| **Layout** | YOLOv8n-DocLayNet → 3 classes (Picture/Table/Formula) | **DocLayNet-v2** or **PP-DocLayout-L**, ideally using the **full class set** (title/list/text/abstract/author…) | Better figure/table recall **and** the ability to emit real Markdown *headings/structure* from layout instead of relying purely on XY-Cut++ line-gap heuristics. |
| **Text OCR** | Indra (DBNet + SVTR; Latin `rec.onnx` + 2,935-token `rec_world.onnx`) | **PP-OCRv4 / PP-OCRv5** (80+ languages, DB++ / SVTRv2 + U-MLKM) or **Surya OCR** (single line-level ViT, strong multilingual + math adjacency) | Higher accuracy on scientific text and far broader script coverage than the current narrow world vocabulary. |
| **Tables** | SLANet + pure-Rust geometric fallback | **PP-StructureV2 (SLANet_Plus)** + add **rowspan/colspan** reconstruction | Current `figure/slanet.rs` flattens to a grid (`max_cols` reconstruction, rejects 1-column tables); merged cells are lost. |
| **Metadata** | GLiNER small + regex fallback | GLiNER v2 (or NuNER) | Modest gain; low priority. |
| **Embeddings** | all-MiniLM-L6-v2 (384-d, INT8 ~22 MB) | **bge-small-en-v1.5** or **gte-small** (opt-in) | Measurably better Obsidian RAG retrieval at similar model size. |

**Formula-model rationale**: The current `markdown.rs` / `figure/latex.rs` heuristics exist largely to repair noisy output from an older formula model. A stronger recognizer (UniMERNet/TexTeller) produces cleaner LaTeX, reducing both error rate and the maintenance burden of the repair code — a compound quality and maintainability win.

## 4. UI / UX Recommendations

### High priority

1. **Finish the Split-Pane Inspector (left pane is empty)** — `ui/src/components/SplitPane.tsx:160–174` renders `activePage.previewUrl`, but nothing in the codebase ever populates `ConversionJob.pages[].previewUrl` (the `ProgressPayload` in `types/index.ts` has no such field). Ship page rasters in the job payload, expose a `/api/page-preview?slug&page` endpoint, or embed pdf.js in the browser build so the "side-by-side source vs Markdown" promise in the ADR/GLOSSARY is actually delivered.
2. **Render Obsidian constructs in `MarkdownViewer`** — verify it renders callouts (`> [!table]-`, `> [!figure]-`), wiki-links `![[...]]`, and image embeds the way Obsidian does, not just KaTeX. The converter emits these heavily, so the preview should match.
3. **Web upload safety** — `crates/server/src/lib.rs` `upload_handler` writes `field.file_name()` straight into `temp/uploads` (path-traversal risk) and never validates `.pdf` or cleans up. Sanitize the filename, reject non-PDFs, and purge temp files.

### Medium priority

4. **Per-job Cancel / Pause** — jobs currently run to completion with no interrupt path from the UI. Add a cancellation signal over the existing broadcast channel and wire a Cancel button into `BatchQueue`.
5. **Real `--help` via clap** — `crates/cli/src/cli.rs` (~32 KB) does manual `args.iter()` / `args.get(idx + 1)` parsing with a hand-written `print_usage()`, even though `clap = { version = "4.5", features = ["derive"] }` is already a workspace dependency. Migrating gives typed parsing, auto-generated help, validation, and shell completions for free.
6. **Web format parity** — the TS type `image_format` is `'jpeg' | 'png'` (`types/index.ts:58`) but the engine supports `webp`. Expose it in `SettingsModal`.
7. **Error surfacing** — failures are folded into the log stream; surface failed jobs inline in `BatchQueue` with a retry action.
8. **Model status refresh** — `ModelsModal` should re-fetch status after `downloadModels()` completes.

### Accessibility & polish

9. **Typography / contrast** — pervasive `text-[10px]` / `text-[11px]` and low-contrast grays hurt readability and accessibility. Move to a semantic design-token system (the three themes are currently hardcoded Tailwind color classes).
10. **Keyboard / focus states** — a `ShortcutsModal` exists, but keep-both-hands navigation needs visible focus rings and ARIA labels on the icon-only buttons.

## 5. Architecture / Maintainability / Security Notes

- **Stale documentation paths**: `IMPROVEMENTS.md` and `FUTURE_IMPROVEMENTS.md` still reference the pre-monorepo `src/pipeline.rs`; update them to `crates/engine/src/…`.
- **Dual-runtime complexity**: the `tract`/`ort` split is the single largest architectural tension. Recommend an ADR (or an amendment to ADR 0001/0005) formalizing a deliberate policy: *which* models run on *which* runtime and *which* execution provider, and whether GPU acceleration is in scope.
- **Singleton sprawl**: `get_indra_engine`, `get_yolo_detector`, `get_latex_engine`, `get_slanet_engine`, `get_gliner_engine`, and `get_embedding_engine` each independently `OnceLock` + load. A single `ModelRegistry` would centralize status reporting (`--doctor`) and memory accounting.

## 6. Suggested Implementation Roadmap

1. **(Quick, high-leverage)** ORT execution-provider selection + `GraphOptimizationLevel::Level3` + explicit thread tuning → re-run `cargo bench --bench ocr_bench` to quantify the delta.
2. **(Quality)** Swap in UniMERNet/TexTeller for formulas and PP-OCRv5 or Surya for text behind the existing `ModelLocator` / feature flags, preserving all current graceful fallbacks.
3. **(UX)** Wire the Split-Pane source canvas + Obsidian-faithful preview + per-job cancel control.
4. **(Engineering)** Migrate the CLI to clap derive; extend world-recognizer batching; add LaTeX/SLANet session pools; sanitize web uploads.

## 8. Model Sizing & Packaging Impact

### 8.1 Baseline context

The dual-flavor packaging strategy already separates binaries from weights: a **Full Offline MSI (~225 MB)** bundles the current model set, while a **Slim MSI (~77 MB)** provisions weights on first launch. The cascading `ModelLocator` (ADR 0014) with zero-copy embedded slices, `--download-models`, `--doctor`, and the `required` / `optional` split in `KNOWN_MODELS` already supports on-demand provisioning. Consequently, a larger model only hard-bakes into the MSI if it is explicitly bundled into the Full build.

> **Note**: Sizes below are order-of-magnitude estimates for ONNX exports and vary by exporter and dtype. The authoritative per-model sizes and SHA-256 hashes are available at runtime via `pdfmd-lite --doctor`.

### 8.2 Estimated size impact by stage

| Stage | Current | Recommended | Quantized (INT8/FP16) | FP32 |
|---|---|---|---|---|
| **Formula OCR** | ~134 MB (RapidLaTeXOCR encoder + decoder) | UniMERNet / TexTeller | ~50–100 MB | ~200–400 MB |
| **Text OCR** | Small (Indra DBNet + SVTR, per-script) | PP-OCRv4/v5 (per-language pack) | +10–40 MB/pack | +40–90 MB/pack |
| **Text OCR (alt)** | — | Surya OCR (multilingual) | ~120–180 MB | ~250–350 MB |
| **Layout** | YOLOv8n-DocLayNet ~11–15 MB | PP-DocLayout-L / DocLayNet-v2 | ~20–45 MB | ~40–90 MB |
| **Tables** | SLANet ~10–20 MB | PP-StructureV2 SLANet_Plus | ~15–35 MB | ~25–50 MB |
| **Embeddings** | MiniLM-L6-v2 INT8 ~22 MB | bge-small / gte-small | ~30–65 MB | ~130 MB |
| **Metadata** | GLiNER-small ~100 MB | GLiNER v2 / NuNER | ~100 MB | ~100–200 MB |

**Dominant growers**: Formula OCR (+100–300 MB) is the single largest increase; **Surya OCR** is the largest *optional* increase (~+300 MB if chosen over PP-OCR). Layout, tables, embeddings, and metadata are comparatively modest.

### 8.3 Net effect on the MSI

- **Slim MSI (~77 MB):** effectively unchanged — weights are never bundled, so model choice has no impact on the shipped installer size.
- **Full MSI (~225 MB today):** grows only for models actually bundled. Bundling everything in **FP32** could push it toward **~500–700 MB**; with **INT8/FP16 quantization and selective bundling** it stays closer to **~250–400 MB**.

### 8.4 Why this matters beyond disk size

1. **RAM, not just storage** — heavier models raise the process-resident base footprint. `concurrency.rs` assumes a **350 MB base**; adopting larger models without re-deriving that budget means fewer page workers at the same RAM, worsening the low-RAM paging failure mode documented in `FUTURE_IMPROVEMENTS.md`.
2. **Cold start** — larger ONNX graphs load slower on first use; the `OnceLock` singletons amortize this only after the first page.

### 8.5 Recommendations to keep the MSI lean

1. **Keep the Slim MSI as the default installer** and never regress it; treat heavier models as on-launch-provisioned assets.
2. **Quantize aggressively** — ship INT8/FP16 ONNX for formula, OCR, layout, and embeddings, where the MB savings are largest and quality loss is minimal.
3. **Make Surya a deliberate decision, not the default** — its multilingual breadth costs ~300 MB; PP-OCR per-language packs are the size-conscious alternative.
4. **Split provisioning by capability** — *core* (OCR + layout), *math* (formula), *tables* (structure), *RAG* (embeddings) — reusing the existing `required` / `optional` model split.
5. **Re-derive the concurrency base budget** whenever a heavier model is adopted, so the Hardware-Aware Concurrency Governor does not silently over- or under-provision.

### 8.6 Bottom line

Model choice has **no effect on the Slim MSI**; it affects only the **Full MSI** and the **on-disk provisioned weight set**. With quantization plus capability-split provisioning, the best-conversion models can be adopted while keeping the shipped installer close to today's footprint.
